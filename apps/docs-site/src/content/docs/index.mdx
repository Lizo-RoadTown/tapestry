## The one sentence

**Tapestry observes the evolving coordination layer between operators and agents, and decides what part of that coordination should become durable structure.**

The shorter version, focused on the loop: *observing how work evolves and deciding what should become durable structure.*

If you remember nothing else from these docs, remember those two sentences. Everything else is one face of them.

## The primary object: the user-agent interface

A **user-agent interface** is a recurring coordination surface where operator intent, agent behavior, project structure, memory, and correction activity meet. Interfaces are the *primary object* Tapestry observes. Projects, architecture, memory, telemetry, and friction are evidence about how interfaces are evolving.

The durable structure being built is **not the project itself**. The durable structure being built is the **evolving coordination layer between the operator and the agents**.

Do not search-and-replace "project" with "interface" in your head. Projects are still important. Architecture is still important. Telemetry is still important. The change is that those things become *context* for understanding interfaces, rather than being treated as the primary object of observation.

## Five things that all turn out to be the same thing

You will see Tapestry described as each of these. All five are true:

1. A memory system (the substrate where interfaces accumulate state across sessions)
2. An observability system (telemetry exposing how interfaces are being exercised)
3. An upskilling system (what happens when an interface stabilizes enough to earn durable structure)
4. A project portfolio system (the same observation loop applied across many projects)
5. A human/agent coordination system (the work happening inside the interfaces)

They feel like different products because they target different surfaces. They aren't different products. They are five faces of *observe interfaces, decide what coordination becomes structure*.

If you ever feel lost in the docs, ask yourself: *which face of the loop is this describing?* That usually resolves the confusion.

The three pages that ground every other page on this site:

- **[User-agent interface](/start/user-agent-interface/)** — the primary object. The recurring coordination surface the platform observes.
- **[Project shape](/start/project-shape/)** — the substrate interfaces live on. A project has observable structure beyond just its code; that structure changes; shape change is evidence of interface change.
- **[What Tapestry is not](/start/what-tapestry-is-not/)** — anchoring against the false analogies (LangSmith, Grafana, AgentOps, Memory MCP, Knowledge Graph, project observability) readers reach for first.

## Why projects plug in

**Intelligence spreads across repositories.** Every Tapestry-consuming project shares one memory store, one cross-agent communication channel, one pattern-recognition layer. Three concrete things flow:

- **Memory persists across sessions and across projects** — a correction you give in one project becomes a binding rule the agent applies next session, and a sibling project's agent sees it too.
- **Agents update each other directly** — a memo written in one project's session is in the next session's auto-recall context for a sibling project, before the operator even types a message.
- **Patterns and skills spread** — repeated behavior the observer notices in one project becomes a candidate; recurring across multiple projects, it becomes a stronger candidate for promotion into a reusable skill every project can invoke by name.

This is the loop applied across many projects rather than one. See [Sharing intelligence across projects](/explanation/sharing-intelligence-across-projects/) for how the mechanism works, and [How the platform upskills itself](/explanation/upskilling/) for how repeated work becomes durable structure (tools, subagents, skills, agents) over time.

## Who this is for

You are setting up a project that plugs into the Tapestry platform. You want the AI agent working in your project to start each session with the platform's accumulated context, follow PROBE discipline (cite sources rather than guess), distinguish runtime concerns from dev tooling, and write friction to memory the moment you correct it.

You do not need to know every internal mechanic. You need to know which files are load-bearing, what each one does, and how to recover when one of them goes missing.
