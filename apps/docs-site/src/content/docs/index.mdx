## What Tapestry is

Tapestry is a user/agent support and reinforcement system.

Projects, interfaces, memory, telemetry, observability, architecture analysis, friction analysis, and upskilling are mechanisms used to observe, strengthen, stabilize, and evolve coordination between the operator and agents.

## The focal phenomenon: user/agent coordination

Coordination is the recurring back-and-forth between the operator and the agents working on their behalf. Operator intent shapes agent behavior. Agent behavior surfaces patterns. The operator corrects. The agent learns. Friction emerges in some places and stabilizes in others. The working relationship matures across changing project conditions, over time.

Tapestry watches that coordination, surfaces what's healthy and what's degrading, and helps recurring patterns crystallize into durable structure that doesn't need to be relearned each session.

Different projects expose different conditions for coordination — different interfaces, different memory requirements, different architectural constraints, different friction patterns. Tapestry tracks each of these because they affect coordination quality.

## The reinforcement mechanisms

Each mechanism the platform uses to reinforce coordination:

| Mechanism | What it does for coordination |
|---|---|
| **Memory** | Persists what the agent has learned about the operator's intent and the project's conditions, so coordination doesn't restart from zero each session |
| **Telemetry** | Surfaces signals about how coordination is being exercised — what tools are called, what's running, what's failing |
| **Observability** | The query API operators and agents use to ask "what's the current state of coordination?" |
| **Architecture analysis** | Detects when project structure changes in ways that affect how operator and agents need to coordinate (services moving, packages merging, interfaces appearing or disappearing) |
| **Runtime analysis** | Detects when actual execution diverges from what coordination predicted |
| **Friction analysis** | Surfaces where coordination is breaking down — operator correcting the same thing repeatedly, agent confusion across handoffs, mismatched expectations |
| **Correction analysis** | Tracks the operator's binding rules as they accumulate; reveals which corrections are landing, which are drifting back |
| **Upskilling** | What happens when a coordination pattern stabilizes enough that it deserves to become a reusable skill, tool, agent, or architecture pattern |
| **Policy** | Decides when a candidate has earned promotion to durable structure |
| **Skill formation** | Materializes earned coordination patterns into reusable callable form |

Projects and interfaces sit elsewhere in the picture. Projects are environments where coordination happens. Interfaces are observable manifestations of coordination inside those environments. The mechanisms above come to bear on coordination between operator and agents, in those projects, through those interfaces.

## Five descriptions, one system

Five ways Tapestry gets described:

1. A memory system — memory is one reinforcement mechanism
2. An observability system — observability is one reinforcement mechanism
3. An upskilling system — upskilling is one reinforcement mechanism
4. A project portfolio system — the reinforcement loop applied across many projects
5. A human/agent coordination system — the coordination being reinforced

Each description names one mechanism the platform uses. Five faces of *reinforce user/agent coordination*.

## Why projects plug in

**Coordination compounds across projects when they share a reinforcement layer.** Every Tapestry-consuming project shares one memory store, one cross-agent communication channel, one pattern-recognition layer. Three concrete things flow:

- **Memory persists across sessions and across projects** — a correction you give in one project becomes a binding rule the agent applies next session, and a sibling project's agent sees it too.
- **Agents update each other directly** — a memo written in one project's session is in the next session's auto-recall context for a sibling project, before the operator even types a message.
- **Patterns and skills spread** — repeated behavior the observer notices in one project becomes a candidate; recurring across multiple projects, it becomes a stronger candidate for promotion into a reusable skill every project can invoke by name.

See [Sharing intelligence across projects](/explanation/sharing-intelligence-across-projects/) for how the mechanism works, and [How the platform upskills itself](/explanation/upskilling/) for how repeated coordination patterns become durable structure (tools, subagents, skills, agents) over time.

## Who this is for

You are setting up a project that plugs into the Tapestry platform. You want the coordination between you and the AI agents working on your behalf to be supported by accumulated memory, observable to you, and improving over time as Tapestry reinforces what's working.

You do not need to know every internal mechanic. You need to know which files are load-bearing, what each one does, and how to recover when one of them goes missing.
