## Who this is for

You are setting up a project that plugs into the Tapestry platform. You want the AI agent working in your project to check memory at the start of a task, follow PROBE discipline (cite sources rather than guess), distinguish runtime concerns from dev tooling, and write friction to memory the moment you correct it.

You do not need to know every internal mechanic. You need to know which files are load-bearing, what each one does, and how to recover when one of them goes missing.

## What this site explains

- The stack of plugins, MCP wiring, hooks, and configuration files that make the agent in your project behave consistently across sessions.
- Why each piece exists. (If you don't know what something does, you will eventually delete or move it. Knowing why prevents that.)
- How to set up a new project so the stack is wired correctly from day one.
- How to recover when the agent starts drifting — usually because something small went missing.

## What this site does NOT cover

Tapestry is a real platform that's actively running. Services are deployed, projects are using it, agents are coordinating through it. This documentation site focuses narrowly on **what keeps a consuming project on track when it plugs into the platform** — the operator-facing pieces.

It does NOT cover:

- **The platform's full architectural design and design philosophy** — the WHY behind how Tapestry is structured at the system level. Those decisions live in the [MANIFESTO](https://github.com/Lizo-RoadTown/tapestry/blob/main/MANIFESTO.md) and the [architecture umbrella doc](https://github.com/Lizo-RoadTown/tapestry/blob/main/docs/architecture/UMBRELLA.md).
- **How Tapestry is being built and migrated** — the engineering plan for moving services from the beta repos into the canonical platform. That lives in the migration docs and ADRs inside the repo.
- **API references for the platform services** — those come later as the services finish migrating into Tapestry's canonical home and stabilize their public contracts.
